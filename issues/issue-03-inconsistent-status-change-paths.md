# Issue 03：課程有 4 種改狀態的路徑，只有 1 種會正確連動點數與出席紀錄

**嚴重程度：高**　**分類：點數邏輯**　**狀態：已修正 (2026-08-17)**

## 修正內容

- `services/course_service.py`：把原本寫在 route 裡的簽到扣點邏輯抽成 `CourseService.checkin_course()`，並新增 `_deduct_for_checkin()` / `_refund_and_release()` 兩個共用 helper，讓「簽到」「標記請假」「編輯彈窗的狀態下拉」三條路徑都走同一套點數邏輯，不再各自為政。
- `update_course()`（對應編輯彈窗的「課程狀態」下拉選單）：偵測到狀態被改成「已完成」時會自動執行跟「簽到出席」一樣的扣點＋出席紀錄；被改成「學員請假」時會自動執行跟「標記請假」一樣的退點（且套用 Issue 02 的「只退已扣過的點」規則）。
- 新增 `refund_deducted_bookings_before_delete()`：刪除課程前，若該課程的預約已經有對應的扣點紀錄，會自動建立退點交易還給學員，不再需要小編自己想到要手動補回點數；刪除成功的訊息也會顯示「已自動退還 N 筆已扣點紀錄的點數」。
- 順手修正一個既有小 bug：簽到時「以課程標題比對學生」的備援邏輯原本寫 `User.role == "STUDENT"`（拿字串跟 enum 欄位比較），改成 `User.role == UserRole.STUDENT`。

## 實測驗證

在 dev 環境用真實 API 呼叫驗證以下 4 條路徑，行為都已一致：
1. 「簽到出席」→ 正常扣點＋標記出席（沒變動）。
2. 建課後直接標記請假（未簽到）→ 不退點（見 Issue 02）。
3. 簽到扣點後，用編輯彈窗把「課程狀態」下拉選單改成「學員請假」（`PUT /api/courses/<id>` `{"status":"cancelled"}`）→ 正確退點。
4. 未簽到的課，用下拉選單直接改成「已完成」（`{"status":"completed"}`）→ 正確扣點。
5. 已簽到扣點的課直接「刪除課程」→ 自動退點後才刪除。

測試完成後已清除所有測試資料。

## 尚未涵蓋的部分

- Booking 本身在課程被刪除時不會跟著軟刪除（只有點數會退還），因此像「學員剩餘堂數統計」頁若沒有另外過濾已刪除的課程，可能仍會把已刪除課程的預約算進出席紀錄。這屬於另一個獨立的資料清理問題，不在本次修正範圍內，如需要可另開 issue 處理。

## 問題敘述

在行事曆「編輯課程」彈窗 (`templates/calendar.html:158-243`) 裡，小編實際上有 **4 種**方式可以改變一堂課的狀態，但這 4 種路徑對「點數」與「出席紀錄」的處理完全不一致：

| 操作入口 | 對應 API | 是否會扣/退點 | 是否更新出席狀態 |
|---|---|---|---|
| ✅「簽到出席」按鈕 | `POST /api/courses/<id>/checkin` (`routes/course_routes.py:242`) | 會扣點（若餘額足夠） | 會，`Booking.status → ATTENDED` |
| 「標記請假」按鈕 | `POST /api/courses/<id>/leave` (`routes/course_routes.py:450`) | 會退點（見 #02，且可能無中生有） | 會，`Booking.status → LEAVE_APPROVED` |
| 編輯彈窗裡的**「課程狀態」下拉選單**（可直接選「已完成」或「學員請假（灰色置頂）」）| `PUT /api/courses/<id>` → `CourseService.update_course` (`routes/course_routes.py:182`, `services/course_service.py:94`) | **完全不會**，只是單純 `setattr` | **不會**，`Booking` 完全沒被動到 |
| 「刪除課程」按鈕 | `DELETE /api/courses/<id>` (`routes/course_routes.py:465`) | **完全不會**（即使這堂課早就簽到扣過點） | 不會（course 被軟刪除，Booking 留在原狀） |

其中第三種（狀態下拉選單）特別容易誤用：小編如果為了「補記錄」直接把課程狀態手動改成「已完成」，會誤以為跟按「簽到出席」效果一樣，但實際上：

```python
# services/course_service.py:94 update_course
for key, value in kwargs.items():
    if hasattr(course, key):
        setattr(course, key, value)   # 純粹改欄位，沒有任何點數/出席副作用
```

`credit_cost` 完全不會被扣、`Booking.status` 也不會變成 `ATTENDED`，等於「這堂課看起來完成了，但學員點數沒少、出席紀錄也不會算進 `student_attendance_stats`」。反過來選「學員請假」也一樣：不會走 `mark_leave`，不會退點、`Booking` 也不會變成 `LEAVE_APPROVED`。

「刪除課程」則是另一個極端：如果這堂課**已經簽到扣過點**，事後發現排錯要刪掉重排，直接刪除課程並不會把已扣的點退還給學員，小編得自己意識到、再手動去「續課管理」用「快速儲值」補回點數。

## 重現步驟

1. 建一堂課，幫學員排課。
2. 打開該課程的編輯彈窗，把「課程狀態」下拉選單直接改成「已完成」，按「儲存更新」。
3. 檢查學員點數 → 沒有變化；檢查該學員的出席紀錄／剩餘堂數統計頁 → 這堂課不會被記錄為已出席。
4. 另外測試：對一堂**已簽到扣點**的課按「刪除課程」→ 學員點數依然維持扣點後的餘額，不會退回。

## 影響

- 小編很容易誤以為「改狀態下拉選單」等同於「簽到」或「標記請假」，造成點數/出席資料實際上沒有被正確記錄，事後對帳會兜不起來且難以察覺（因為 UI 上課程看起來狀態是對的，只有點數餘額是錯的）。
- 刪除已完成課程時遺漏退點，需要小編自己記得手動補救，容易漏掉。

## 建議修復方向

- 讓「課程狀態」下拉選單改為「已完成」或「已取消」時，後端也呼叫對應的簽到 / 請假邏輯（或乾脆把下拉選單拿掉，統一只能透過「簽到出席」「標記請假」兩個有完整副作用的專屬按鈕來改變課程結局狀態）。
- 刪除課程前，若偵測到該課程已有對應的 `DEDUCTION` 交易紀錄，跳出提示或自動生成退點交易，避免小編忘記手動退點。
