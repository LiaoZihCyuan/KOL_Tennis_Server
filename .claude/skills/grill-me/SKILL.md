# Grill Me

在改任何程式碼或設定之前，先自己把事情查清楚，給使用者一份完整的提案，取得同意後才動手。
簡單的事不要拿來一題一題討論。

## 規則

1. **先調查，再提案。** 動口之前先查：讀相關程式碼、在本機重現、看資料與 git 歷史，找出原因與可行做法。
   - 查事實是我的工作，不是使用者的。能從程式碼、資料、環境查到的，一律自己查，不要問。
   - 需要翻多個檔案或查 production 的，派一個 sub-agent（全新 context）去查；一兩個指令就能查到的直接查。
2. **一次給完整提案**：原因（查到了什麼）、要改哪些檔案、各改什麼、怎麼驗證。
   細節上我能判斷的就直接採用最合理的做法並寫在提案裡，使用者不同意再指出來改。
3. **只有真正屬於使用者的決定才提問**：需求不明確、業務規則、有實質差異的取捨、會影響客戶資料的事。
   - 這類問題跟提案一起列出，每題附上我的建議答案與理由，讓使用者可以直接說「照建議」。
   - 如果某個決定會讓整個做法完全不同（要不要做、範圍、方向），先單獨問這一題，得到答案再寫提案，免得白做調查。
4. **不要憑空想像需求。** 使用者沒提的功能、重構、「順便」的改進，一律不做；想到了就在提案裡提出來，由使用者決定。
5. 使用者明確說「可以」才開始動手。使用者只改了其中幾點時，更新後的計畫要重新列一次確認。
6. 實作中發現計畫需要偏離（例如原本的做法行不通），**停下來回報並重新確認**，不要自行改方向。

## 適用範圍

- 需要先確認：程式碼（routes/services/models/templates/static/utils/migrations 等）、設定
  （Docker、compose、`.dockerignore`、`.gitignore`、部署與工具腳本、`.claude/settings*.json`、hooks、agents、skills）。
- 不需要確認，可直接更新：`CLAUDE.md`、`.claude/lessons-learned.md`、`e2e_artifacts/` 下的測試腳本、Claude 的私人記憶。
- 使用者明確說「直接改」或已經講清楚具體改法的，就照著做，不必再追問。
